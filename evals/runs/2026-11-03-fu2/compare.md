| Visible text | S3 gives you four server-side encryption options. SSE-S3 is the default for every bucket, and every new object upload is automatically encrypted at rest. To use something else, you can specify the encryption type in your PUT requests or change the default encryption configuration on the destination bucket.<br><br>1. SSE-S3: server-side encryption with Amazon S3 managed keys, the default. S3 encrypts each object with a unique key, encrypts that key with a regularly rotated key, and uses 256-bit AES-GCM. There are no additional fees for SSE-S3.<br><br>2. SSE-KMS: server-side encryption with AWS KMS keys. It lets you centrally manage KMS keys and define policies controlling how and by whom they can be used. The KMS keys must be in the same Region as the bucket. There are additional charges for using KMS keys. S3 Bucket Keys can cut KMS request costs by up to 99 percent.<br><br>3. DSSE-KMS: dual-layer server-side encryption with KMS keys. It applies two independent layers of AES-256 encryption. It helps meet compliance standards that require multilayer encryption. It costs more than standard SSE-KMS because of the extra processing overhead and AWS KMS API calls. S3 Bucket Keys aren't supported for DSSE-KMS.<br><br>4. SSE-C: server-side encryption with customer-provided keys. You manage the keys while S3 handles encryption and decryption, and you must supply the key with each request.<br><br>If you want to change the bucket's default encryption rather than specifying it per request, only SSE-KMS or DSSE-KMS are available as alternatives to SSE-S3. Changing the default doesn't re-encrypt existing objects. To do that, you can use S3 Batch Operations with the Copy objects action. |

| Visible text | The third one, DSSE-KMS: it applies two independent layers of AES-256 encryption to objects as they're uploaded. The first layer encrypts your data with a unique data encryption key generated by AWS KMS, and the second layer encrypts the already-encrypted data again with a separate AES-256 key managed by Amazon S3. It's aimed at compliance standards that require multilayer encryption and full control of your encryption keys.<br><br>The tradeoffs versus standard SSE-KMS are slightly higher latency from the extra encryption processing, and higher charges from the added computational overhead and additional AWS KMS operations. S3 Bucket Keys aren't supported for DSSE-KMS, so you can't use them to cut KMS request costs. The KMS keys must be in the same Region as the bucket, and the S3 checksum in the object's metadata is stored in encrypted form.<br><br>To enforce it, you can use a bucket policy that denies s3:PutObject unless the request includes an x-amz-server-side-encryption header requesting DSSE-KMS. The policy condition checks that s3:x-amz-server-side-encryption equals aws:kms:dsse. You can also make it the bucket default, since SSE-KMS and DSSE-KMS are the options for a non-SSE-S3 default encryption configuration.<br><br>If you use replication, note that S3 doesn't replicate objects encrypted with SSE-KMS or DSSE-KMS by default. You need to add the ID of a symmetric customer managed KMS key in the Destination element and opt in with the SourceSelectionCriteria element. The replication role also needs kms:Decrypt on the source key and kms:Encrypt on the key protecting the replica. |
