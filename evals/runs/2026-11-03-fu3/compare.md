| Visible text | S3 gives you four server-side encryption options. SSE-S3 is the default for every bucket, and every new object upload is encrypted at rest automatically. To use a different type, you can specify it in your PUT requests or change the default encryption configuration on the destination bucket.<br><br>1. SSE-S3: server-side encryption with Amazon S3 managed keys, the default. S3 encrypts each object with a unique key, encrypts that key with another key it rotates regularly, and uses 256-bit AES-GCM. There are no additional fees for it.<br><br>2. SSE-KMS: server-side encryption with AWS KMS keys. It lets you centrally manage KMS keys (create, rotate, disable, schedule deletion) and define policies for who can use them. The KMS key must be in the same Region as the bucket, and AWS KMS charges apply. S3 Bucket Keys can cut KMS request costs by up to 99 percent.<br><br>3. DSSE-KMS: dual-layer server-side encryption with AWS KMS keys. It applies two independent layers of AES-256 encryption, which helps meet compliance standards that require multilayer encryption. It has slightly higher latency and higher cost than standard SSE-KMS. S3 Bucket Keys aren't supported with it.<br><br>4. SSE-C: server-side encryption with customer-provided keys. You manage the keys while S3 handles encryption and decryption. You provide the key with each request, and S3 purges it from memory after use.<br><br>SSE-S3 is the default, so you only need to act if you want something else. As a bucket default, you can set only SSE-KMS or DSSE-KMS. SSE-C can only be specified per request. Changing the bucket default doesn't re-encrypt existing objects. | Visible text | The third one, DSSE-KMS: it applies two independent layers of AES-256 encryption to objects as they're uploaded, which helps you meet compliance standards that require multilayer encryption and full control of your keys. It applies two independent layers of AES-256 encryption. The first layer encrypts your data with a unique data encryption key generated by AWS KMS, and the second encrypts the already-encrypted data again with a separate AES-256 key managed by Amazon S3.<br><br>The tradeoff is overhead. It has slightly higher latency, and it costs more because of the extra computation and additional AWS KMS operations. As with SSE-KMS, the KMS key must be in the same Region as the bucket, and the object's checksum is stored in encrypted form. S3 Bucket Keys aren't supported for DSSE-KMS, so you can't use them to cut KMS request costs.<br><br>To enforce it, you can use a bucket policy. The documented example denies s3:PutObject unless the request includes an x-amz-server-side-encryption header requesting DSSE-KMS. The condition checks that s3:x-amz-server-side-encryption equals aws:kms:dsse.<br><br>One thing to watch if you replicate: by default, S3 doesn't replicate objects encrypted with SSE-KMS or DSSE-KMS. You have to add the ID of a symmetric customer managed KMS key in the Destination element and explicitly opt in by adding the SourceSelectionCriteria element. |
